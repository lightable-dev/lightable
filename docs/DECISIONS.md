# Decisions

Choices the spec left open, and why. Follow these unless a later entry here
replaces one. When you make a new call the spec doesn't cover, add it here.

## M1

1. **Unknown data keeps raw text.** `Unknown` entities, raw tables, raw
   sections, header variables and `extra` lists store each value as the
   original text (`Pair { code, raw }`), not as a parsed `Value`. This lets
   the M3 writer reproduce unknown data byte-for-byte. `Unknown::group_codes()`
   and `Pair::value()` give the typed view. (The spec sketched
   `Vec<(i16, Value)>`.)
2. **Header values are accessors.** `Header` holds every variable in file
   order; `version()`, `insunits()`, `extmin()` etc. read from that list, so
   there is one source of truth.
3. **Known entities keep leftovers in `extra`.** Codes a parsed entity doesn't
   use (XDATA, `102 {...}` groups, `999` comments, unrecognised codes) go into
   `Entity::extra` in file order. Subclass markers (`100`) are dropped; the
   writer regenerates them. `Layer::extra` works the same way.
4. **Malformed → `Unknown` + warning.** A bad number, missing required field,
   negative radius, or invalid colour, lineweight, handle or flag turns a known
   entity into `Unknown` (all pairs kept) with a warning. Zero radius is
   accepted.
5. **Duplicate table names:** the first entry wins; the duplicate is kept in
   `Table::unparsed` with a warning.
6. **Damaged files:** a tokenizer error after the first `0 SECTION` keeps
   what was read plus a warning; garbage before any section is
   `DxfError::NotDxf` or a syntax error. Missing `ENDSEC`, `ENDTAB` and `EOF`
   are warnings.
7. **Arc angles** are stored in degrees, as in the file.
8. **`999` comments outside sections** are kept as stray records, without a
   warning (the format allows them anywhere). *(Changed in M2 part B; they
   were dropped before.)*
9. **Licence:** `MIT OR Apache-2.0`, with `LICENSE-MIT` and `LICENSE-APACHE`.
10. **Versions:** `Version` covers R12, R13, R14 and 2000–2018 (R13/R14
    added in M2). Other `$ACADVER` values still load, with a warning;
    `Header::acadver()` returns the raw string.
11. **Encoding:** replaced by M2 part B decisions 4–9 (the Latin-1 fallback
    is gone).

Also settled:

- **No `dxf` crate.** The reader is written from scratch with no dependencies;
  the spec's "evaluate the `dxf` crate" step was dropped after M1.
- **Corpus:** `tests/corpus/` is generated by `tools/gen_corpus.py` (keep them
  in sync). Files that can't be redistributed go in the git-ignored
  `tests/corpus-private/`; the corpus tests load them when present.

## Corpus (before M2)

- **All corpus drawings are our own.** `tools/gen_sources.py` draws 13 drawings
  with ezdxf; `tools/convert_corpus.sh` re-saves them through other writers.
  No third-party drawings, so everything in `tests/corpus/` is redistributable.
- **Writers and routes.** ODA File Converter writes R12 and 2000–2018.
  FreeCAD 1.1 writes R14 only (its `DxfVersionOut` setting is ignored headless).
  LibreDWG's `dxf2dwg` cannot read the ezdxf sources, so LibreDWG gets a DWG
  2018 made by ODA and writes DXF with `dwg2dxf`.
- **Incomplete outputs are rejected, not committed.** A converted file must
  start with a SECTION and end with EOF. LibreDWG 0.14 silently stops after
  BLOCKS for 9 of 13 drawings in R2004+ (exit code 0); those are logged in
  `SOURCES.md`, not added.
- **Size split:** files over 5 MB go to the git-ignored `tests/corpus-private/`.
- **The exhaustive damaged-input sweep** in `tests/corpus.rs` covers only the
  small hand-written files; real-writer files are too big for every-byte
  truncation. Proper fuzzing is M2.

## M2 part A

1. **Streaming reader, borrowed tokens.** The tokenizer yields `Token<'a>`
   with the value borrowed from the input (`raw: &'a str`); the reader keeps
   one token of lookahead and copies a value only when the model stores it.
   This took the 50 MB load from 3.1 s to about 1 s; allocation was most of
   the time. `tokenizer::Token` changed shape (public API, pre-1.0).
2. **Benchmark:** `cargo bench -p lightable-dxf --bench load` (no dependencies)
   times `read_bytes` on the private 50 MB file, or on a synthetic ~50 MB
   file when that is absent (e.g. in CI). It prints a warning above 2 s
   rather than failing, since CI machine speed varies.
3. **Child records are nested.** `VERTEX`s and the closing `SEQEND` live in
   `Polyline::vertices` / `Polyline::seqend`; `ATTRIB`s and their `SEQEND`
   in `Insert::attributes` / `Insert::seqend`. Children are full `Entity`
   values (own handle, layer, ...) with `EntityKind::Vertex` / `Attrib`; the
   `SEQEND` is kept as an `Unknown` entity so its handle survives. An
   `INSERT` collects following `ATTRIB`s whether or not group 66 is set.
4. **Orphaned children** (`VERTEX`, `ATTRIB`, `SEQEND` without a parent) are
   kept in place with a warning. When one repeats the handle of a child of
   the preceding entity, the warning says so.
5. **Embedded objects:** from group `101` on (R2018 `MTEXT`/`ATTRIB`
   "Embedded Object"), pairs go to `extra`, like XDATA, because they reuse
   codes the entity itself uses.
6. **`extra` stays in file order** across categories (`102` groups, embedded
   objects, unknown codes, repeats of known codes, XDATA).
7. **First occurrence wins** for codes a simple entity reads once; repeats
   go to `extra`. Codes that are lists (LWPOLYLINE vertices, SPLINE knots,
   weights and points, LTYPE elements, MTEXT `3` chunks) are read in order.
8. **Count checks:** an `LWPOLYLINE` vertex count (90), `SPLINE` knot,
   control and fit counts (72/73/74), weights vs control points, and `LTYPE`
   element count (73) must match what follows, or the record is kept
   verbatim with a warning.
9. **Text is not decoded yet.** `Text::value`, `MText::text` and attribute
   values are stored as written (not trimmed); `\U+XXXX`, `%%d` and MTEXT
   formatting codes are left for the encoding work in M2 part B.
10. **Dimensions:** group 70's low 4 bits pick the type (0–6, including
    ordinate and 3-point angular, beyond the spec's four); the remaining
    bits are kept in `Dimension::flags`. Each type reads only its own point
    codes; any others go to `extra`. Dimension variables in `DIMSTYLE` are
    kept as raw pairs (`DimStyle::variables`) until dimension rendering (M7).
11. **`DIMSTYLE` handle is group 105 only.** Group 5 in a `DIMSTYLE` record is
    the DIMBLK variable (an arrow block name), which R12 files use.
12. **Shape-file text styles** (`STYLE` with flag 1) have empty names; tables
    accept any number of empty-named entries and never look them up by name.
13. **Blocks** are a `Table<Block>` keyed by case-insensitive name. A block
    whose header can't be parsed, or that repeats a name, is kept verbatim
    (through its `ENDBLK`) in `blocks.unparsed` with a warning. Group 3 is
    dropped when it repeats the name. `ENDBLK` pairs are kept in `Block::end`.
14. **Defaults when optional codes are missing** follow the DXF reference:
    scale 1, width factor 1, text style `STANDARD`, ellipse 0..2π, MTEXT
    attachment 1, INSERT 1×1 array.
15. **Bulge maths** lives in `lightable_geom::bulge` (`arc_from_bulge`); `lightable-dxf`
    stores bulges as read and uses `lightable-geom` only in its tests.
16. **Known-bad corpus files.** LibreDWG 0.14's R14/R2000 output (18 files)
    repeats `VERTEX`/`ATTRIB` records after their `SEQEND` and writes an
    extra `ENDBLK`, all with duplicate handles. The reader reports these;
    `tests/corpus.rs` lists the files and allows only those warnings for
    them. Every other corpus file loads with no warnings except encoding.
17. **No true aligned dimension in the corpus:** ezdxf writes
    `add_aligned_dim` as a rotated linear dimension (type 0). Type 1 is
    covered by unit tests only.

## M2 part B

1. **Nothing parsed is dropped.** Misplaced records (pairs outside any
   section, junk between tables, an `ENDBLK` outside a block, pairs before the
   first entity, pairs before the first header variable, data after `EOF`)
   are kept in `Drawing::stray` as `StrayRecord { section, index, pairs }`,
   with a warning. `index` counts the items before it in that place
   (sections, header variables, tables, blocks or entities) so a writer can
   put it back where it was. Orphaned `VERTEX`/`ATTRIB`/`SEQEND` records stay
   in the entity list as before.
2. **Unreadable tails are kept as text.** When the tokenizer hits a line it
   cannot read (a bad group code, or a code with no value), everything from
   that line on is stored in `Drawing::unparsed_tail` with a warning. The
   pairs can't be recovered past that point, but the text is not lost.
3. **`ATTDEF` is parsed** (`EntityKind::AttDef`): the `ATTRIB` fields plus the
   prompt (group 3, stored as written).
4. **Which bytes are which encoding.** The reader sniffs `$ACADVER` and
   `$DWGCODEPAGE` from the raw bytes (first 1 MB) before decoding:
   - R2007+ (`AC1021` and later): UTF-8. If the bytes are not valid UTF-8,
     they are decoded with the code page, with a warning.
   - Older files: bytes that are valid UTF-8 are read as UTF-8, silently
     (some writers, e.g. LibreDWG and FreeCAD, write UTF-8 into R14/R2000
     files that declare ANSI_1252); otherwise the declared code page is used.
   - Missing or unsupported `$DWGCODEPAGE` with non-UTF-8 bytes: ANSI_1252,
     with a warning. Bytes invalid in the code page become U+FFFD, with a
     warning (the only lossy case).
   - `Drawing::encoding` records the result: `Utf8`, or `CodePage(n)` (also
     for ASCII-only pre-2007 files, so a writer knows what to use).
5. **Supported code pages:** ANSI_874, 932, 936, 949, 950 and 1250–1258, via
   `encoding_rs` 0.8.35 (pinned; MIT OR Apache-2.0, data BSD-3-Clause).
   ANSI_1361 (Johab) and DOS code pages are not supported.
6. **Text values are decoded, originals kept.** `Text::value` (TEXT, ATTRIB,
   ATTDEF), `MText::text` and `Dimension::text_override` hold the decoded
   string; `raw_value` / `raw_text` / `raw_text_override` hold the string as
   written, only when decoding changed it (`None` otherwise, so plain text
   costs nothing extra). A writer writes the raw form when it still decodes
   to the current value, and encodes the value otherwise.
7. **Escapes decoded:** `\U+XXXX` (exactly four hex digits; surrogates stay
   literal), `\M+nXXXX` (n = 1 Shift-JIS, 2 Big5, 3 Korean, 5 GBK; 4 Johab
   stays literal), `%%d` → `°`, `%%p` → `±`, `%%c` → `⌀` (U+2300 DIAMETER
   SIGN), `%%%` → `%`, `%%nnn` → character `nnn` in the drawing's code page
   (single-byte pages only). Codes are case-insensitive. `%%o`/`%%u`
   (overline/underline toggles) and malformed escapes are left as written.
8. **MTEXT decoding keeps formatting.** In MTEXT only the character escapes
   are decoded (`\U+`, `\M+`, `%%d/p/c/%`); formatting codes (`\P`,
   `\f...;`, ...) stay, and `\\` (an escaped backslash) is left alone so
   `\\U+0041` is not mistaken for an escape. `%%nnn` is a TEXT-only feature.
9. **Names are not decoded.** Layer, style, block and linetype names are
   stored as written (after byte decoding), including any `\U+` escapes, so
   references between them keep matching. The prompt of an ATTDEF is also
   stored as written.
10. **Fuzzing.** `crates/lightable-dxf/fuzz` (cargo-fuzz 0.13.2, libfuzzer-sys
    0.4.13 pinned) has three targets: `tokenizer`, `reader` (`read_bytes`)
    and `text` (`decode_text`/`decode_mtext` on every code page). It is its
    own workspace and needs nightly; it is dev tooling only, so libFuzzer's
    NCSA licence (BSD-style) does not reach anything shipped (now a rule in
    CLAUDE.md). CI does not
    run it. `tools/fuzz.sh SECONDS` seeds every target from `tests/corpus`
    and the regression inputs and runs them in parallel, without a sanitizer
    (no `unsafe` code; overflow and bounds checks stay on; about 20× faster)
    and with inputs up to 16 KB. Crashing inputs go in
    `tests/fuzz-regressions/`, which a normal test replays.
    **First 1-hour run (2026-10-10, Intel Mac, three targets in parallel):**
    no crashes, no timeouts. reader 6.7 M runs (~1,860/s, 2,905 coverage
    edges), tokenizer 209 M (~58,000/s, 103 edges, flat), text 7.0 M
    (~1,950/s, 468 edges). Peak memory 67 MB. `tests/fuzz-regressions/` is
    therefore empty apart from its README.
11. **Linear-time leftovers.** `Fields::leftovers` and the orphan-parent
    lookup no longer rescan earlier pairs/entities, so huge records can't
    make the reader quadratic.

## M3

1. **Save-back is byte-identical when nothing changed.** `Drawing::source`
   keeps the bytes the drawing was read from. `save_bytes` (and `to_bytes`
   for the same version) re-reads them and, if that gives a drawing equal to
   the current one, returns them unchanged: stray records, the unparsed
   tail, original text, formatting and undecodable bytes all survive. All
   198 corpus files save back byte-for-byte. `Source` never affects
   equality (it is provenance, not content). Cost: the source bytes stay in
   memory (50 MB for the 50 MB file), and the check re-parses on save.
2. **Edited drawings are regenerated, not patched.** A changed drawing is
   written by the generator, in R12 if it was R12 and R2018 otherwise, with
   a warning when that changes the version. Reusing the original text for
   unchanged records of an edited file is left for when editing exists (M5).
3. **Two passes: normalise, then format.** The writer first makes a valid
   copy of the drawing for the target version (handles, owners, required
   tables, block records, layouts, R12 downgrades), then formats it. Writing
   is deterministic, so read → write is a fixpoint: writing what was read
   gives the same bytes and an equal drawing (tested for the whole corpus,
   both versions).
4. **Handles.** Existing handles are kept; missing ones are assigned above
   every handle in the input; duplicates get new handles, with a warning.
   `$HANDSEED` is one above the highest handle written. R12 output has
   handles on entities, children and `ENDBLK` (as ODA writes R12), with
   `$HANDLING 1`; table entries and `BLOCK` records have none.
5. **Owners (R2018).** Computed from the structure, never trusted from the
   input: entities → `*Model_Space`/`*Paper_Space` record; block contents,
   `BLOCK` and `ENDBLK` → their block record; `VERTEX`/`ATTRIB`/`SEQEND` →
   their parent; table entries → their table. Every block gets a
   `BLOCK_RECORD`; files without layouts (R12, R13/R14) get an
   `ACAD_LAYOUT` dictionary with `Model` and `Layout1` linked from the
   records. Existing OBJECTS are copied as they are.
6. **Required content is added.** Missing defaults (layer `0`, linetypes
   `ByBlock`/`ByLayer`/`Continuous`, style and dim style `Standard`,
   `VPORT *Active`, `APPID ACAD` and every XDATA application) and anything
   entities refer to but the drawing lacks (layers, linetypes, text styles,
   dim styles, empty blocks) are added, with warnings for the latter.
7. **What generated files leave out, with warnings:** stray records, the
   unparsed tail, orphaned `VERTEX`/`ATTRIB`/`SEQEND`, unparsed table
   entries and blocks, and block records without a block. These are kept
   by save-back only.
8. **R12 downgrades.** `LWPOLYLINE` → `POLYLINE` (exact: bulges, widths,
   elevation); `ELLIPSE` → polyline (5° steps) and `SPLINE` → polyline (16
   points per knot span, NURBS with weights) via `lightable_geom::curve`, 2D at
   their elevation or 3D if not flat; `MTEXT` → one `TEXT` per line,
   formatting removed, placed by attachment point; true colour → nearest
   ACI (approximate palette, `Color::aci_rgb`); lineweights, the invisible
   flag, newer codes and non-XDATA leftovers dropped; `SOLID`, `TRACE`,
   `3DFACE`, `SHAPE` kept without newer codes; other types (`HATCH`,
   `LEADER`, `MULTILEADER`, `XLINE`, `RAY`, `VIEWPORT`, ...) dropped; extra
   layouts dropped; complex linetypes become plain dashes; header limited
   to R12 variables; tables filtered to R12 groups; CLASSES and OBJECTS not
   written. Every loss is a warning, counted per kind.
9. **R12 names.** Names longer than 31 characters or with characters
   outside the code page are renamed (unusable characters → `_`, unique
   with `~n`), and every reference is updated (entities, blocks, layers,
   header `$CLAYER`/`$CELTYPE`/`$TEXTSTYLE`/`$DIMSTYLE`). Application names
   over 31 characters are dropped with their XDATA.
10. **Version-specific records.** Entities of types defined in CLASSES
    (e.g. `MULTILEADER`) are not copied into a different version: their
    record layout changes between versions and ODA drops such copies. They
    are dropped with a warning (same-version writes and save-back keep
    them). R2018 output also drops entity types that are neither standard
    nor in CLASSES (no program can read them).
11. **Encodings.** R2018 output is UTF-8. R12 output uses the drawing's code
    page (`Drawing::encoding`, else `$DWGCODEPAGE`, else ANSI_1252);
    characters outside it become `\U+XXXX` (or `?` beyond U+FFFF) with a
    warning. Text keeps its original form (`raw_value` etc.) when that
    still decodes to the current value; otherwise the value is written.
12. **Undecodable bytes are kept (fixes M2's one lossy case).** Bytes that
    are not valid in the code page are read as `U+F700 + byte` instead of
    U+FFFD, and the code-page encoder writes them back as the same byte. In
    UTF-8 output they stay private-use characters, with a warning.
13. **Formatting.** Group codes right-aligned in three columns, CRLF line
    endings, floats in the shortest form that reads back exactly (with a
    decimal point; exponent form below 1e-6 or from 1e15), MTEXT split in
    250-character chunks. `read_str` is now `read_bytes` on the text's
    bytes, so both report the same encoding.
14. **API.** `Drawing::to_bytes(version)`, `write_file(path, version)`
    (R12 or R2018; other versions are `DxfError::UnsupportedVersion`),
    `generate_bytes(version)` (never reuses the source), `save_bytes()`,
    `save_file(path)`. `lightable convert|generate|save` exposes them.
15. **`lightable-dxf` depends on `lightable-geom`** (curve flattening for R12). Neither
    has UI dependencies, so the spec's separation still holds.
16. **External validation.** `tools/validate_written.py` writes every
    corpus file as R12 and R2018 and checks it with our reader, ODA File
    Converter and FreeCAD (see `tests/corpus/WRITE_VALIDATION.md`). ODA
    repairs silently instead of warning, so "opens without warnings" means:
    ODA's re-save of our file differs from it no more than ODA's re-save of
    the original corpus file does, and FreeCAD prints no problem messages.
    Result: 396 of 396 clean.
17. **Write speed is not a target yet.** The 50 MB file saves back in about
    1.5 s after loading (re-parse plus copy) and generates in about 3 s
    (R2018) or 4 s (R12).

## M4

1. **`lightable-render` reads `lightable_dxf::Drawing` directly** for now: `lightable-core`
   has no document model until M5, and the spec's "lightable-render draws from the
   document held in lightable-core" can be met by then without changing the
   scene types. `lightable-render` depends on `lightable-dxf` and `lightable-geom` only — no
   UI — so M4b's visual diff reuses it as is.
2. **Scene, then outputs.** `lightable_render::build` turns a drawing into a
   `Scene`: styled primitives in world XY (paths with bulges, fills,
   points, text lines), with layers, colours (BYLAYER, BYBLOCK, ACI, true
   colour), linetypes, block references (nested, arrays, layer-0 and
   BYBLOCK inheritance) and OCS already resolved. `svg::to_svg` and
   `tess::tessellate` (GPU vertex data) are both views of the scene.
3. **What is drawn.** Model space only (layouts are M7). Drawn: LINE,
   CIRCLE, ARC, LWPOLYLINE, POLYLINE (2D, 3D, spline-fit, polyface and
   polygon meshes), ELLIPSE, SPLINE, POINT, TEXT, MTEXT, ATTRIB, INSERT,
   DIMENSION (its block), SOLID, TRACE, 3DFACE, LEADER (its vertices),
   constant ATTDEFs inside blocks, ATTDEF tags at top level. Not drawn,
   counted in `Scene::skipped` and shown in the status bar: HATCH,
   MULTILEADER, VIEWPORT, XLINE, RAY, IMAGE, WIPEOUT and other types.
4. **Simplifications for M4:** lineweights are not shown (like a CAD
   program with lineweight display off); MTEXT is laid out line by line
   without word wrapping or inline formatting; text width factor and
   oblique angle are kept in the scene and SVG but ignored on screen;
   mirrored inserts draw their text readable, not mirrored; an off layer
   hides only what is on that layer (frozen insert layers do not hide the
   block's other layers); the on-screen font has no CJK glyphs.
5. **Arcs and transforms.** OCS uses the arbitrary axis algorithm
   (`lightable_geom::transform`). Arcs stay exact (bulges) when the transform
   keeps circles circular seen from above; under non-uniform scale or a
   tilted plane they are flattened (5° steps) first. Mirroring flips bulge
   signs.
6. **Linetypes** are scaled by `$LTSCALE`, the entity's group 48 and the
   block reference's scale; dashes are in world units. Patterns so fine
   that a path would get more than 20,000 repeats are drawn solid.
7. **GPU drawing.** eframe 0.36.2 with the glow (OpenGL 3 / WebGL2)
   backend — the spec suggested wgpu; glow is smaller, works the same on
   desktop and in browsers, and is enough for coloured lines. Vertex data
   is built once per drawing in chunks of (layer, cell of a 16 × 16 grid);
   vertices are `f32` offsets from the chunk centre, and the chunk-centre
   minus view-centre offset is computed in `f64` each frame, so precision
   is relative to the view (tested at 1e9). A frame only culls chunks
   (hidden layers, off screen) and draws. Lines are 1 px.
8. **Level of detail.** Each chunk with arcs also has a coarse version
   (30° segments) used while its largest arc is under 30 px on screen;
   this took the 100k-entity benchmark's 95th-percentile frame from 19 ms
   to 15 ms.
9. **Text on screen** uses egui's text renderer (not GPU geometry): only
   text at least 4 px tall and on screen is drawn, at most 5,000 per
   frame. CAD text height is the cap height, so the font size is height /
   0.7.
10. **Interaction:** middle-drag or left-drag pans (there is no selection
    until M5), wheel and pinch zoom around the cursor, double middle click
    or the toolbar button zooms to extents of the visible layers, layer
    checkboxes toggle visibility, drag-and-drop opens a file (also in the
    browser).
11. **Golden snapshots.** `tests/snapshots/<corpus file>.svg` (198 files,
    about 2 MB), compared by `lightable-render/tests/snapshots.rs`; mismatches
    are written to `target/snapshots-new/`, and `UPDATE_SNAPSHOTS=1`
    accepts them. SVG uses numbers with at most 4 decimals, so changes
    show as small text diffs and side by side on GitHub. Background #212121
    and ACI 7 = white, as on screen.
12. **Frame-rate check.** `lightable --bench FILE [FRAMES]` animates pan and
    zoom with vsync off and prints frame times. On this machine (Intel
    Mac): 100k entities (`tests/corpus-private/big_100k__ezdxf__R2018.dxf`,
    112,500 items, 5.2 M vertices) average 7.5 ms, 95th percentile 15.2 ms,
    worst 21.7 ms; the 275k-entity file averages 8.9 ms, 95th percentile
    18.8 ms. `lightable --shot FILE OUT.ppm` saves a screenshot of the window
    (no screen capture of other windows). These need a display, so CI does
    not run them.
13. **WebAssembly from the start.** `lightable` builds for
    `wasm32-unknown-unknown` (CI job `wasm32`, with clippy); on the web it
    runs in the `cad_canvas` canvas of `crates/lightable/index.html` (since
    preview preparation: `web/index.html`, built by `tools/build_web.sh`; for
    trunk) and opens dropped files. The toolchain file installs the target.
14. **`lightable` commands.** `lightable [FILE]` now opens the viewer; the old
    summary is `lightable info FILE` (the validator uses it).
15. **MTEXT plain text** moved into `lightable-dxf` (`MText::plain_lines`,
    `mtext_plain_lines`), used by both the R12 writer and the renderer.

## M4b

1. **Own crate, UI-free.** `crates/lightable-diff` depends on `lightable-dxf`,
   `lightable-geom` and `lightable-render` only. `lightable_diff::diff(a, b, &options)`
   returns a `Diff`; `lightable_diff::view` turns it into recoloured scenes; the
   app only uploads and draws them. `Diff::to_json` writes the report by
   hand (no serde in the library; `serde_json` is a dev-dependency for
   the tests).
2. **What is compared.** Model-space and paper-space entities (as
   separate places), the contents of named block definitions (anonymous
   blocks such as `*D1` dimension pictures are regenerated by every
   program and are skipped; the DIMENSION entity itself is compared), the
   layer table (added, deleted, colour, linetype, lineweight, on, frozen,
   locked, plot) and two header variables that change what the numbers
   mean: `$INSUNITS` and `$LTSCALE`. Everything else in the header
   (`$HANDSEED`, `$TDUPDATE` and the other timestamps, current layer, ...)
   is ignored. Never compared: handles, owners, reactors, subclass
   markers, entity order, the way numbers are written. Other tables
   (text styles, linetypes, ...) are not compared yet.
3. **Entities as labelled values** (`lightable_diff::features`): common
   properties (layer, colour, linetype, lineweight, visibility, extended
   data) and the entity's own content, each value tagged as a name, text,
   length, angle, plain number, position or direction. Details in plain
   words come from these labels ("radius changed from 4 to 6", "end moved
   by (0, 10)", `text changed from "LIVING" to "LOUNGE"`). If every
   position moved by the same vector and nothing else changed, the detail
   is "moved by (dx, dy)". A change counts as a geometry change when the
   content differs; property-only changes (layer, colour) are reported
   with `geometry: false`.
4. **Interpretation choices.** TEXT is placed by its first point for
   left/baseline, aligned and fit text and by its second point otherwise
   (writers fill the unused point differently). MTEXT is compared as its
   words (`plain_lines`) plus, separately, its formatting codes. INSERT
   attributes are compared by tag, not file order. A SPLINE with fit
   points is compared by its fit points only: ODA adds the control points
   it computes, which is not a change. SOLID, TRACE and 3DFACE are read as
   four corners (libredwg writes elevation as group 38 instead of per-
   corner z). HATCH is partly interpreted: pattern name, solid fill,
   scale and angle by name, then the boundary, the pattern lines and the
   rest as raw data. Any other type we do not interpret is compared as
   raw data (numbers rounded to 1e-6, handles and owner links removed);
   its changes are marked **uncertain**, with the group codes that differ.
   Changes to types the viewer cannot draw are marked **not shown** and
   get a dashed box in the views.
5. **Tolerance:** lengths within 1e-6 × the drawings' diagonal are equal
   (`DiffOptions` can set a relative or absolute tolerance); angles within
   1e-6° modulo 360; plain numbers to about 1e-9 relative.
6. **Matching, in phases** (each on what the earlier ones left):
   identical (same handle first, then by content in a grid of buckets);
   then, if handles are trusted, same handle and type = changed; then for
   entities that cannot be matched by handle: moved by one vector
   (preferring the vector most entities share), same geometry with other
   properties, nearby (same type and layer, overlapping extents, ranked by
   how many values are equal; a guess between several candidates is
   marked uncertain). What is left is added or deleted.
7. **When handles are trusted.** Handles are used only if at least half
   of the identical pairs share their handle. A program that renumbers
   everything (ezdxf rebuilding a drawing, the `renumbered` pair) fails
   this, and matching falls back to content; edits made by a program that
   keeps handles pass it. With trusted handles, a deleted entity and a new
   one with another handle stay deleted + added even if they look alike
   (the `hatch_boundary` pair): we report what the file says.
8. **Same drawing, other entities.** After matching, leftovers on both
   sides that draw exactly the same lines, arcs and points (exact
   interval coverage within 10 × the tolerance, mutual, repeated until
   stable) are "redrawn": a polyline saved as separate lines and arcs, a
   full ellipse whose end parameter was rounded. They are not changes;
   they are counted (`Diff::equivalent`) and listed separately
   (`Diff::redrawn`, `"redrawn"` in the JSON, a collapsed section in the
   app) so nothing is silently ignored. Text is not geometry here.
9. **FreeCAD findings** (FreeCAD 1.1 re-saving an ezdxf drawing): with
   ezdxf's default `$INSUNITS = 6` (metres) it scales everything by 1000;
   it renames every entity's layer after its own object (Shape, Shape001,
   ...); it splits LWPOLYLINEs into LINEs and ARCs; it explodes block
   references but leaves every part at the block origin; it drops TEXT,
   MTEXT, HATCH, SOLID and DIMENSION; it rounds the ellipse end parameter
   to 6.28318. The `freecad_resave` pair therefore uses millimetres, has
   no blocks or text, and expects zero *geometry* changes: the layer
   renames are reported as property changes and the split polyline as
   redrawn.
10. **Test data** (`tests/diff/<pair>/a.dxf, b.dxf, expected.json`): made
    by `tools/gen_diff_pairs.py` (ezdxf) and, for `freecad_resave/b.dxf`,
    `tools/freecad_resave.py`. Expected changes give kind, type, handle
    and words the details must contain. Accuracy: 28 of 28 expected
    changes found, 0 missed, 0 extra (precision 1.000, recall 1.000);
    3 no-change pairs (renumbered, R2018 vs R2000, FreeCAD re-save) with
    0 geometry changes.
11. **Cross-writer check (corpus, not a test):** ezdxf originals against
    ODA R2018 and R2000 re-saves report no entity changes except
    LEADER/MULTILEADER raw-data differences (marked uncertain) and true
    colours reduced to ACI in R2000 (correct); libredwg R2018 also drops
    LWPOLYLINE widths (a real difference, reported). R12 and FreeCAD
    conversions report real representation changes (ellipses and splines
    approximated by polylines, MTEXT exploded).
12. **Speed.** Entities are first compared as records (`==`); the value
    lists are only built when that fails. The 50 MB drawing (275k
    entities) against itself: 1.8 s for the diff after 2 s reading both;
    with every handle changed and the order reversed (content matching
    only): 4.3 s. `cargo run --release -p lightable-diff --example timing A B
    [--renumber]` measures it.
13. **Views.** Overlay: B in grey with added green and changed yellow
    on top of A's deleted entities in red and A's version of changed
    entities in dark yellow; layers merged by name. Side by side: A and B
    each recoloured, one shared pan/zoom. A change list (with "not shown",
    "uncertain" and "properties only" notes), "Next change" / "Previous"
    (and the N key) zooming to each change (at least 5 % of the drawing
    wide) with a white frame, and "Export JSON" (native: written next to
    B as `<B>.changes.json`; web: copied to the clipboard). Only
    model-space changes are zoomable; paper, block, layer and setting
    changes are listed. Compare is opened with `lightable --diff A B
    [--side]`, by dropping two files at once, or with "Compare with…"
    then dropping the newer file. `lightable diff A B [--json OUT]` prints
    the changes.
14. **JSON report** `lightable-diff/1`: `a`, `b`, `tolerance`,
    `handles_trusted`, `summary` (added, deleted, changed, unchanged,
    equivalent, not_shown, uncertain), `redrawn` and `changes`; each
    change has kind, place, type, layer, handle, details, geometry,
    shown, certain, old/new (handle, index, layer) and bounds
    `[xmin, ymin, xmax, ymax]` or null.
15. **`lightable-render` additions:** `Item::entity` (the entity an item was
    drawn from), `build_with(d, paper_space)` and `build_block(d, name)`.
    Limitations: a changed block definition is reported in the block, not
    on each reference to it; changes inside arrays and nested blocks are
    shown on the reference.

   (`tools/gen_example.py`, ezdxf, millimetres, `$INSUNITS = 4`), with a
   sheet border and title block. Rev C has exactly 4 design changes (one
   hole moved 5 mm, one hole Ø12 → Ø14, thread note M12 → M16, a 10 × 10
   chamfer on one corner), a revision cloud around the chamfer and the
   title block's revision letter. Rev C is Rev B edited in place, so
   handles are kept. The apartment plan is kept as the second example
   (`plan-rev-a/b.dxf`, renamed from `example-rev-a/b.dxf`).
3. **Headlines in plain words, mechanically true** (`lightable_diff::words`,

   changed from 12 mm to 14 mm", "Text changed from M12 to M16", "Polyline
   corner at (200, 160) chamfered 10 × 10 mm". Every part comes from the
   values compared: moves are split into right/left/up/down; circles are
   named by diameter; a chamfer is reported only when one vertex is
   replaced by two points that lie on its two edges with a straight
   segment between them (a curved one is "rounded"); other vertex changes
   are counted. Lengths carry the unit named by `$INSUNITS` (of B, else A)
   and none otherwise; angles carry "°". The exact property values stay in
   `details` (shown under "Details").

   (`Change::markup`, `words::is_markup`): a closed polyline made only of
   arcs (a revision cloud), and anything on a layer whose name starts with
   TITLE, BORDER or REV. The summary counts design changes ("4 changes
   found between Rev B and Rev C") and adds "plus 2 revision markups";
   the list shows markup under its own heading, after the design changes.
   This is a stated rule on names and shapes, not a guess about intent;
   JSON reports it per change (`markup`) and in `summary.markup`.

   2: the change list as headlines; a click zooms (smoothly, to at least a

7. **Instant preview on the web.** While the wasm loads, the page shows
   the default example's overlay and, next to it, its change list: the
   summary line, the design-change headlines and the revision markup. Both
   are made when the page is built (`tools/build_web.sh` runs
   `crates/lightable-diff/examples/web_preview.rs`): the SVG from the
   comparison's overlay scene, the list from the JSON diff report the app
   exports. Nothing is checked in, so they cannot go stale; a test keeps
   the example's names in the build script the same as in the app. The
   preview is hidden when `?example=` names another example, and removed
   when the app starts.
8. **Download progress.** `web/main.js` fetches the wasm itself and passes
   the response on through a byte-counting stream, so
   `WebAssembly.instantiateStreaming` still compiles while it downloads
   (the browser tests record that call). The bytes counted are unpacked,
   so the percentage is against the unpacked size the build writes into
   the page; with a compressed response the Content-Length is the packed
   size and would overshoot.
9. **No emoji fonts.** egui's `default_fonts` feature is off; the app
   installs only Ubuntu-Light (text) and Hack (monospace) from
   `epaint_default_fonts`, dropping Noto Emoji and the emoji icon font
   (743 kB). Hack is also the fallback of the proportional family: it
   has the ◀ ▶ of Previous / Next, which Ubuntu-Light lacks. A test reads
   the fonts' character maps and fails if any character the app writes
   has no glyph (egui's own `has_glyph` misreports characters of its
   replacement-glyph font, so the test does not use it). egui uses
   emoji-font glyphs only in widgets the app does not use (submenu arrows,
   key names, inspection panels).
   Drawing text with ☑ ✔ ★ ⚠ or similar now shows egui's replacement
   glyph. The fonts are under the Ubuntu Font Licence 1.0 and the Hack
   licence (MIT with Bitstream Vera), both allowed for bundled fonts by
   CLAUDE.md.

10. **Smaller web download.** `tools/build_web.sh` builds with the
    `wasm-release` profile (opt-level "s", LTO, one codegen unit, no debug
    info; "z" came out larger, 6.68 MB against 5.57 MB) and runs
    `wasm-opt -Oz` (binaryen; required in the Pages workflow). Measured in
    Chrome with DevTools' "Fast 3G" conditions (562.5 ms, 180 kB/s), from a
    server that compresses like GitHub Pages:

    | Build | wasm | gzip | First content | App ready |
    |---|---|---|---|---|
    | lightable.dev before | 6.62 MB | 2.41 MB | "Loading…" only | 16.2 s |
    | + size profile | 5.57 MB | 2.15 MB | | 15.8–17.0 s |
    | + no emoji fonts | 4.82 MB | 1.69 MB | | 12.4–13.3 s |
    | + wasm-opt -Oz (now) | 3.92 MB | 1.59 MB | list 0.7 s, preview 1.25 s | 11.6–12.0 s |

    `node tools/web_browser_test.mjs chrome URL OUT --throttle` repeats the
    measurement (OUT/timing.json).

11. **Summary wording.** First screen, for any files: "N changes found
    between X and Y", beside it "plus revision markup (M items, including
    K revision cloud(s))", the cloud part left out when K is 0. "Items"
    because markup is counted per drawing object (the bracket's revision
    table row is four of them), and layers 1–3 never say "entities". K
    comes from `Change::revision_cloud` (shape detection, also in the JSON
    report as `revision_cloud` and `summary.revision_clouds`), not from
    headline text. A built-in example may carry a note shown under the
    summary ("Example: the drafter clouded only the bolt note."); it
    describes the example file and is never shown for the user's files.
    The PNG report header and the web preview use the same words.

## Rules for M5 (decided before M5)

1. **Saving an edited drawing keeps its DXF version and copies every
   unchanged record exactly; only edited records are regenerated. Nothing
   is dropped on save.** This replaces M3 decision 2 (edited drawings are
   regenerated as R12 or R2018) for saving; R12 and R2018 stay the targets
   of an explicit "Save As" conversion. It needs per-record source spans
   and a writer for records of every version the reader accepts.
2. **Unchanged files save instantly using a dirty flag instead of
   re-reading.** This replaces the re-read comparison of M3 decision 1:
   edits go through the document (M5's command engine), which marks what
   changed.
3. **Target: saving a 50 MB file takes under 2 s before v0.1.**
